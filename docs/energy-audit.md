# Endless Crown energy audit

This audit accompanies the Ultra 2 battery controls on October 2–3, 2026. The first optimization pass narrowed statistics observation and reused the scrolling-idle timer during continuous input. After the October 3 masked statistics comparison favored original behavior, the normal source restores original statistics observation. The isolated timer comparison favored timer reuse; the subsequent approved changes also reuse the visible-menu timer and batch frequent preference writes. Effect selection, the haptic call per handled scroll change, live counters, and animations remain intact. Measured battery savings have not been established.

## Evidence boundaries

- Source inspection establishes which operations run per scroll; it does not measure their energy cost.
- The accepted battery trials use a signed diagnostic Release build with XCTest supervision, neutral wake taps, and no attached profiler. They measure reported charge for the whole Watch.
- Runtime profiling passes are separate and labeled `profiling-only`; their battery readings are excluded from the baseline.
- Synthetic replay changes the app's selected-row binding. It does not reproduce all physical Crown input, inertia, or system haptics.

## Findings that do not explain per-scroll cost

- `WidgetCenter.reloadAllTimelines()` is called after the 1.5-second scrolling-idle timer fires and on other explicit actions/session end. It is not requested on each continuous scroll change.
- The measured settings have `menuHidden: true`. `revealMenuButton` returns through the hidden-menu branch and does not allocate the menu-auto-hide timer in these trials. A visible-menu configuration has additional timer resets and needs its own comparison.
- `ambientModeEnabled` changes visual styling. It does not give the app authority over watchOS display sleep.
- The tested number system is decimal. Source inspection alone does not establish expensive number formatting as a bottleneck.

- Preference setters, haptic selection and motor requests, row rendering, and diagnostic workload/display policies are unchanged.

## Subsequent overhead changes, October 3

The user authorized menu-timer reuse and preference batching while preserving the original haptic path. Normal Release retains original `@StateObject` statistics observation, haptic effect mappings, Random progression, scroll-change guards, and live counter/peak-speed recording. A source comparison confirms `triggerHaptic`, `resetRandomState`, `onPatternChanged`, `checkAndRebalance`, and the live `recordHaptic` algorithm match the original source. The handler only changes the final current-number preference update into a staged save. Timer reuse and batching do not throttle, debounce, or skip haptic requests, but identical calls do not establish identical felt feedback.

The visible-menu hide timer now reuses its valid timer and moves the deadline to three seconds after the latest interaction. Hidden/open-menu and disappearance paths still cancel it. The existing scrolling-idle timer reuse retains its 1.5-second deadline. The earlier hidden-menu trials did not measure the menu-timer allocation path.

`HapticStats` batches the frequently changed total, peak speed, and shared current number. A single non-repeating timer submits the latest dirty values on a nominal two-second schedule during continued input; later input does not postpone that batch. The timer uses the main run loop's common modes to remain eligible during tracking, and is cancelled on an early save. Saves also occur at scrolling idle before complication reload, on scene inactivity/background, at session boundaries, and before explicit reset/number-system refresh. Counter reset replaces any pending shared number with zero, preventing a stale batch from restoring the old number. Other settings, streak/session counters, spin-time persistence, and base-offset updates retain their immediate behavior.

Live statistics still publish each change. The complication's shared data can lag until the next batch during active scrolling. Abrupt termination can lose data not yet submitted in that batch; two seconds is a scheduled interval, not a guaranteed maximum under run-loop delay. `UserDefaults` itself saves asynchronously, so the save method does not guarantee an immediate disk commit. See [Apple's UserDefaults documentation](https://developer.apple.com/documentation/foundation/userdefaults).

Host verification passed 55 statistics checks, 16 report checks, four tests of the source-extracted menu method, and 23 Python checks: 98 total. These cover live publications, continued-input saving, explicit-save/reload behavior, resets, session-end data, missing app-group storage, timer identity/deadlines, and cancellation/resumption. The menu method runs in a macOS state holder, with explicit class capture added for compilation; it is not a mounted Watch view. The signed normal Release build passed, its signature verified, and diagnostic markers were absent. The Watch was disconnected during preparation, so installation and physical acceptance were pending at this checkpoint. No matched CPU profile or battery saving is established. Evidence is retained in `energy-test-results/overhead-optimization/3c589199-f2cd-4615-a7de-02e81b5b278e/`, including frozen prior sources, build logs/provenance, verification logs, and source checks.

Future comparison preparations default to `before,overhead-only`. New diagnostic flags preserve original menu allocation and per-event preference behavior for the reference variant; existing frozen trials are not rewritten or reused as acceptance for this pass.

## Automated overhead comparison, October 3

Four accepted ten-minute Clicks runs used two timed app scroll changes per second, matched XCTest neutral-wake supervision, and the same frozen source/toolchain. The original variant restores original timer allocation and immediate preference writes; both variants retain original statistics observation and haptic logic. Original/optimized/optimized/original order produced reported charge changes of **65% → 65%, 65% → 60%, 60% → 55%, and 55% → 50%**. Each run recorded 1,199 scroll changes, 1,199 haptic requests, and 26 acknowledged wake touches. All four passed report/configuration/build-identity validation; all 88 samples were active, unplugged, not in reduced luminance, and nominal in temperature.

The optimized variant showed ten total reported percentage points of loss over twenty measured minutes; the original showed five. This pilot does not demonstrate savings, and its coarse whole-Watch readings, two repetitions per build, different starting charge, and between-run history do not establish a reliable regression or its cause. The hidden menu leaves menu-timer savings untested. API requests do not measure delivered motor pulses, and this fixed-rate replay does not test very fast physical Crown feedback. There is still no matched CPU profile to show whether timer reuse and preference batching reduce runtime work or introduce offsetting overhead.

Startup initially required entering the Watch passcode on the prompt raised by the UI-test runner. Earlier foreground-interrupted attempts were excluded. The final slot's first attempt was interrupted by a Time to stand notification at 2:50 p.m.; the automatic retry completed with settings unchanged. The normal optimized app was restored and opened successfully after all four accepted runs. Raw reports, excluded attempts, signed variant provenance, verification, and restoration evidence are retained in `energy-test-results/overhead-energy-compare/32695491-dcd7-4360-bd03-dc1a2deb805f/`.
